# 再生成の手順書(GTFSの取り直しと時刻表の作り直し)

- 作成日: 2026-09-24(開発者質問「GTFSの再取得と再生成、どう進めるのがいい?」)
- 対象環境: 外付けSSD上のプロジェクト(Mac)。Python 3.10以上+pandas/numpy/jpholiday
  (前提の詳細は docs/handover.md §8)

## 0. なぜ必要か

配っている時刻表データの有効期限は `webapp/data/meta.json` の `valid_until`
(2026-09-30)。これは9フィードのうち最も早く切れる calendar.txt の end_date。
過ぎると画面に「きょうはこの時刻表の対象外の日です」と出る。
**応募は2027-01-11で、審査期間中もサイトは動いている必要がある。**

## 1. 更新するもの / 凍結するもの(いちばん大事な区別)

| | 扱い |
|---|---|
| **第3部(時刻表Web)** | **更新する**。「いま乗れる時刻」が命なので、新しいフィードで作り直す |
| **第2部(交通空白マップ)の確定数値** | **凍結する**。15,418人・43.2%・571人などは2026-06-10のダイヤで確定済み(README・応募資料と一致)。新フィードで計算し直すと数値が動き、資料と食い違う |
| 第1部(大活字PDF) | 時刻表を更新したら**同じダイヤで作り直す**(紙とWebの不一致は実害が出る) |

`output/` と `data/target_meshes.csv` などの分析成果物は**触らない**。
`export_web_data.py` は `REFERENCE_DATES` しか見ず `TARGET_DATE`(=分析日)を使わないので、
時刻表の再生成が空白マップの数値を動かすことはない(確認済み)。

## 2. 手順

### ① 旧フィードを退避する(必須)

`download_gtfs.py` は **`gtfs_◯◯/` が既にあるとスキップする**ので、退避しないと
新しいものが手に入らない。退避先の名前は必ず `gtfs_` で始めること
(`.gitignore` の `gtfs_*/` に引っかからないと、数十MBのフィードがgitに入ってしまう)。

```
mkdir -p gtfs_archive_20260610
mv gtfs_山形交通 gtfs_上山市 gtfs_山形市 gtfs_天童市 gtfs_山辺町 \
   gtfs_中山町 gtfs_東根市 gtfs_南陽市 gtfs_寒河江市 gtfs_kaminoyama gtfs_archive_20260610/
```

**旧フィードは消さないこと。** 確定数値を再現できる唯一の現物(handover §7の警告)。

### ② 新しいフィードを取得

```
python3 gap_map/download_gtfs.py
```

### ③ 新しい有効期間を確認する

```
for d in gtfs_*/; do echo "$d"; head -2 "$d/calendar.txt"; done | head -40
```

`end_date` がいちばん早いフィードが、全体の有効期限になる。

### ④ 日付の設定を新しい期間に合わせる

`gap_map/region.py` の `REGION` を編集する:

- `reference_dates` … 平日・土曜・日祝の代表日。**新しい有効期間の中**の、
  祝日やお盆にかからない普通の週の3日を選ぶ
- `date_table_start` … きょうのダイヤ判定表の開始日(ふつうは再生成の月の1日)
- `valid_until` … ③で調べたいちばん早い `end_date`
- `target_date` は**変えない**(第2部の分析日。凍結数値の再現用)

### ⑤ 時刻表を作り直す

サブ地区を増やす判断(docs/plan_f10_stop_select.md §6.7)をするなら、
**この再生成と同時にやる**。いちばん重い工程なので2度回さない。

```
# (サブ地区を増やす場合だけ)
python3 gap_map/make_subdistricts.py --apply --far-dist 1200 --far-pop 150 --far-ratio 0.10 --max-k 6
python3 gap_map/make_mesh_index.py

python3 gap_map/export_web_data.py
```

### ⑥ 検算

- `webapp/data/meta.json` の `valid_until` が新しい日付になっているか
- 合計サイズと1地区あたりの大きさ(サブ地区を増やしたなら見込みと合うか)
- 全ファイルに `kantan_board` が入っているか
- **d23→県立中央病院を1ペア、事業者の公式時刻表と突き合わせる**
  (従来の「第1部PDFと一致」は旧ダイヤのPDFとの比較なので、ダイヤが変わった今回は使えない)
- 画面を開いて「きょうは◯◯ダイヤです」が出ること(対象外の日でないこと)

### ⑦ 第1部のPDFを作り直す

```
python3 make_pair_timetable.py
```

### ⑧ コミット

`webapp/data/` は生成物だがコミットする例外(handover §7)。
再生成のたびに全ファイルが洗い替わるので、**1回の再生成=1コミット**にまとめる。

## 3. 罠

- `download_gtfs.py` は既存フォルダをスキップする(①をやらないと何も起きない)
- 退避先の名前が `gtfs_` で始まらないと、フィードがgitに入る
- フィードが更新されると**確定数値は再現できなくなる**。旧フィードを消さない
- 再生成のたびにgitの履歴が時刻表のぶん(50MB〜)増える

## 4. いつやるか(推奨)

1. **いま1回**(10月ダイヤ。有効期限が延びる。サブ地区の判断が決まっていれば同時に)
2. **応募直前にもう1回**(2026年12月末〜2027年1月初旬。審査期間をカバーする)

フィードの有効期限は事業者の都合で決まるので、②の時点で `valid_until` が
審査期間をカバーしているか確認する。足りなければ審査期間中にもう1回必要になる。
