## 1. いまの実験ページ(nearby)をそのまま持ち込めない理由

案Dの実験ページ `webapp/nearby/` は「探索エンジンが正しい」ことは示したが、かんたんモードが
この3か月で積み上げた**時刻表の作り方**を持っていない。

| かんたんモードにあるもの | 実験ページ(nearby) |
|---|---|
| 1日分の全便を、ごぜん/ひる/ごご/よるの時刻チップで出す | 指定時刻から4本だけ |
| **帰り**(施設→家) | 行きのみ |
| 直通優先・乗換は直通の隙間だけ(GAP_FILL)・乗換の代表1本化 | なし(最速の1本) |
| 乗り場選び(5分ルール・便の少ない停を外す・曜日ごと) | 最速の停 |
| 同じバスに早く出て乗るだけの便を消す | なし |
| 同じバスが止まる近くの停(board_options / alight_options) | なし |
| 済生病院シャトル(f20専用)・運休日(10/15など) | なし |
| 乗換で「降りる停≠乗る停」の案内(transfer.off) | なし |
| のりかたカード・時計モード・音声・印刷・電話番号欄 | 簡易表示 |

この「作り方」は全部 Python の工場(`gap_map/export_web_data.py`)にある。
段階3の本体は、**工場の1地点ぶんの処理をJSに移植すること**で、画面はほぼ今のものを使い回す。

## 2. 全体像

```
[今]  地区をえらぶ → 代表点で事前計算したJSON(地区ファイル)を読む → 画面2・画面3
[段階3で追加]
      わが家(端末に保存した位置) → 配布ネットワーク(0.18MB)を読む
                → webapp/engine/timetable.js が「地区ファイルと同じ形」の答えを作る
                → 同じ画面2・画面3 で表示
```

**要は「地区ファイルと同じ形の答え」を端末で作ること**。こうすると:

1. 画面3の描画(のりかたカード・チップ・印刷・音声)は**1行も分岐させずに**使い回せる
2. **検算が自動でできる**: 地区の代表点を「わが家」として JS に計算させれば、
   すでにある地区ファイル(Python の答え)と**完全一致するはず**。全地区(時刻表62ファイル)×38施設×3ダイヤ×行き帰りを
   機械で突き合わせられる(段階1bと同じ守り方。「検算できない計算結果を配らない」原則を維持)

## 3. 画面の流れ(3タップを壊さない)

### 画面1(地区をえらぶ)に、いちばん上に1つだけ足す

```
┌─────────────────────────────┐
│ 🏠 わが家から しらべる              │ ← わが家が登録済みのときだけ出る(1タップで画面2へ)
├─────────────────────────────┤
│ 📍 いまいる場所を わが家にする       │ ← 未登録のとき。家にいるときに1回だけ押す
├─────────────────────────────┤
│ ① おすまいの地区をえらんでください   │ ← 今のまま(GPSなし・登録しない人の道)
│  [第一] [第二] [第三] …            │
└─────────────────────────────┘
```

- タップ数: **わが家(1) → 行き先(2) → 時刻チップ(3)**。今と同じ3タップ
- 登録は「家にいるときに1回」。測位の誤差が300mを超えるとき(パソコンのIP推定など)は
  登録させず、地区の一覧に案内する(今の GEO_ACC_STOP_M と同じ線)
- 位置は**端末の中だけ**に保存し、どこにも送らない(地図ボタンで外に出るのはバス停の座標だけ、は今と同じ)
- 「わが家を けす」ボタンを画面1の下に小さく置く

### 画面2(行き先をえらぶ)

- 施設一覧は今と同じ。「ぜんぶで約◯分」の目安は、わが家からの計算値に置き換える
- 計算が終わるまでは一覧だけ先に出し、目安の数字はあとから埋める(待たせない)

### 画面3(時刻表)

- 中身は今と同じ部品。違うのは次の3点だけ:
  - ①の「あるいて約◯分」が**わが家からの徒歩分**になる(代表点からの目安ではなくなる)
  - 「いちばん近いバス停」欄は、わが家ありのときは不要(すでに家から測っている)。
    「◯◯から のる」で乗り場を選び直す機能は残す
  - 電話番号欄(デマンド交通・市の窓口)は地区ごとの情報なので、わが家の位置から
    メッシュ索引で地区を自動で引いて出す(利用者には地区を選ばせない)

### URL(ハッシュ)

- `#home/f09` のように書く(座標はURLに入れない)。わが家が未登録の端末でこのURLを開いたら、
  画面1に戻して「わが家が とうろく されていません」と出す

## 4. 移植するもの(webapp/engine/timetable.js)

工場の関数を、**1地点・1ダイヤ種別ぶん**だけ動くように移植する。名前は Python と同じにして、
対応がたどれるようにする。

| Python(export_web_data.py) | 役目 |
|---|---|
| `build_origins`(expand_by_route) | 家の徒歩圏で「別の系統を持つ停」も候補にする |
| `build_targets` / `nearby` | 施設側・家側の徒歩圏の停 |
| `scan_from_origin` | 乗れる便を1本ずつ試す(直通+乗換1回は隙間だけ) |
| `collapse_transfer_alternatives` / `keep_useful_boards` / `frontier_rows` | 乗換の代表化・役に立たない乗り場を落とす |
| `drop_same_bus_earlier_rows` | 早く出て同じバスに乗るだけの便を消す |
| `board_options_for` / `alight_options_for` | 同じバスが止まる近くの停 |
| `make_itinerary`(transfer.off・headsign2・bp/ap を含む) | 1便の表示用データ |
| `pick_kantan_board` / `_board_typical`(曜日ごと) | おすすめの乗り場 |
| `build_entry` | 地区ファイルの1エントリの形にまとめる |

移植で気をつける点(段階1の教訓):

- **距離の計算式**: 実験ページは簡易式(distM)を使っているが、工場は
  `compute_access.nearby_stops` の haversine。徒歩圏800mの境目や徒歩分の丸めが1つずれると
  便が変わるので、**工場と同じ式**にする
- **丸め**: Python の round() は銀行家丸め(raptor.js の `pyRound()` を使う)
- **並べ替えの順番**: 同着・同時刻のときの順番を Python と同じにする(sorted は安定ソート)

### ネットワーク側に足すもの(gap_map/export_network.py)

- **済生病院シャトル入りのネットワーク**を別ファイルで配る(`network/weekday_f20.json` など)。
  工場と同じく「f20 の行き・帰りだけ、このネットワークで計算する」(restricted_feeds の考え方を踏襲)
- 運休日(`closed_dates`)は今の meta.json をそのまま使う(画面側の withoutClosed が効く)

3-2 の照合は**ランダムでなく全件**。代表点で一致すれば「わが家」でも同じ計算が走るので、
残るリスクは「代表点では起きないが、ある家の位置で起きる」ケースだけになる。これは
3-2 の後半で、**メッシュ817個の中心点**を「わが家」にして Python 側でも同じ計算をし、
突き合わせることで潰す(Python に「任意の1地点ぶん」を出す小さな関数を足す)。

### 5.1 3-1 計測の結果(2026-10-07。通過)

`gap_map/measure_browser_timetable.js`(新規・読み取り専用。Node で実行)。scan_from_origin の
重い部分(別系統の停も候補にする乗り場選び → 乗れる便を1本ずつ試す → 直通しない行き先だけ RAPTOR)を
素直に移植して、平日ダイヤ(いちばん便が多い)で測った。この Mac での実測、スマホ想定はその4倍。

| 測ったもの | 中央値 | 最大 | スマホ想定(最大×4) | 関門 |
|---|---|---|---|---|
| 行き38施設(地区の代表点 62点) | 7ms | 509ms(第一地区) | 2.0秒 | ✅ 1秒 / 3秒以内 |
| 行き38施設(**メッシュ中心 817点=住む場所の全体**) | 5ms | 516ms(七日町〜山形駅の都心) | 2.1秒 | ✅(95%の点は 67ms 以内・1秒超は0点) |
| 帰り1施設(いちばん重い施設) | 503ms | 535ms | 2.1秒 | ✅ |

```
node gap_map/measure_browser_timetable.js                 # 地区の代表点(行き+帰り)
node gap_map/measure_browser_timetable.js weekday meshes  # メッシュ817点(行き)
```

分かったこと:
- 重いのは**停が集まる都心だけ**(乗り場15〜24か所・乗れる便が約1,000本・RAPTORも約1,000回)。
  郊外の家は数ms で終わる
- 38施設のうち1つでも直通しない施設があれば、便ごとに RAPTOR を1回回すので、RAPTOR の回数は
  「乗れる便の数」とほぼ同じになる。それでも1回あたり0.5ms 程度で、計算量の心配はいらない
- 帰りは家の場所ではなく**施設側の乗り場の多さ**でほぼ決まり、どの施設でも 0.5秒前後
- **画面での待ち時間の見込み**: 画面2で行き38施設(最大0.5秒・スマホ2秒)、画面3で選んだ施設の帰り
  (最大0.5秒・スマホ2秒)。画面を固めないよう Web Worker で回し、§3 のとおり一覧を先に出す
- 計測は計算の重い部分だけ。表示用の整形・乗り場の絞り込みは軽い処理なので、3-2 で全部を
  移植したあとにもう一度同じスクリプトで測り直す
- スマホ想定の「×4」は仮定。3-4 で実機の時間も測る

## 7. 危ないところと手当て

| 危険 | 手当て |
|---|---|
| 計算が遅い(便ごとに乗換探索を回すため、都心の家では数百回) | ①Web Worker で画面を固めない ②画面2は施設一覧を先に出し目安はあとから ③画面3は選んだ施設の行き帰りだけ計算(1施設なら軽い)④それでも遅ければ「乗換の探索は直通が無い時間帯だけ」という工場の条件をそのまま使って回数を減らす(すでにそうなっているので、まず 3-1 で実測) |
| JS と Python の答えがずれる | 3-2 の全件照合。ずれたら配らない。CI でも小さなネットワークで回す(段階1の乱数テストと同じ仕組み) |
| ブラウザの保存領域が消える(わが家が消える) | 消えても地区の一覧で今までどおり使える。消えたことを画面1で知らせる |
| 古い app.js と新しいネットワークの組み合わせ | 今と同じ版番号(?v=)と no-cache 読み込み |
| データ期限(11/20)後の再生成で JS 側だけ古くなる | ネットワークも地区ファイルも同じ runbook で再生成。照合スクリプトを runbook の手順に入れる |

## 8. 作品として言えること(応募資料向け)

  家のそばのバス停からの時刻表が出せるようになる(サブ地区109MB案・F10フル版296〜423MB案は不要)

- 端末の中の計算が Python の工場と**全件一致**することを機械で確かめてから配っている
