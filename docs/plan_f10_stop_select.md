## 0. 要求(2026-07-07 開発者)

> 乗るバス停、おりるバス停を選択できるようにできませんか?
> (GPSが利用可能な環境であれば、現在地から近いのいくつかの場所から選択できるように)

対応の内訳:

| 要求 | 状態 |
|---|---|
| GPSで近い**地区**の候補から選ぶ | **実装済み**(コミット 09aad0b。両モードの📍ボタン) |
| **乗るバス停**を地区内の停留所から選ぶ | 本検討書の対象(データ再設計が必要) |
| **おりるバス停**を選ぶ | **非推奨と回答済み**: エンジンが施設徒歩圏800mの全停留所から「バス到着+徒歩の合計が最短」の停を便ごとに選択済み。選ばせると合計で遅い選択肢を提示することになる |

## 1. なぜ現状ではできないか(復習)

- Webアプリは計算しない(事前計算JSONの表示のみ)が根本設計
- 乗車側の事前計算は「地区代表点の最寄り停留所+150m以内(=同じ場所の別のりば)」に
  意図的に絞っている(export_web_data.py の SAME_PLACE_M)。徒歩圏800m全体を候補に
  すると、実測で1地区19停留所・1日3,567便が候補になり出力が破綻したため
- したがって「別の停留所から乗る」時刻表は**存在しない**。作るには停留所ごとの
  事前計算が必要

## 2. 設計案

### 案A: 停留所単位の事前計算+オンデマンド読み込み(フル版)

- 対象停留所: 地区の全メッシュ(住民がいる250mメッシュ)から徒歩圏
  (config.MAX_WALK_TO_STOP_M=800m)内の全停留所
- 出荷物(追加分):
  - `webapp/data/stops/{地区ID}.json` … 停留所索引(表示名・かな・lat/lon・
    のりば統合キー)。GPSの近傍候補と選択UIに使う
  - `webapp/data/timetables_stop/{地区ID}/{停留所キー}.json` … その停留所発の
    地区→38施設の時刻表(構造は現行の地区JSONと同じ)
- 読み込みは選択時のみ(初期表示は現行どおり地区代表)→ 実行時の重さは増えない。
  増えるのは**リポジトリとGitHub Pagesの容量**と**Macでの生成時間**
- URL設計: 現行 `#dNN/fNN` は不変(QR=F7も不変)。停留所指定は `#dNN/sKK/fNN`
- UX: かんたんモードの3タップは死守(画面3のカード下に小さく
  「べつのバス停から のる」を置く程度)。本体はしっかりモードの停留所ピッカー+
  GPS近傍停留所の候補表示

### 案B: 控えめ版(地区あたり主要2〜3停留所に限定)

案Aと同じ仕組みで対象停留所を便数上位2〜3に限定。データ2〜3倍で収まるが、
「家の近くの停留所が入っていない」が起こり、要求を部分的にしか満たさない。

### 案C: ブラウザで経路計算(否定)

「Webは計算しない」根本設計に反する。検算不能な計算結果を配ることになるため採らない。

## 3. 未知数と実測方法(着工判断の前に必ず実行)

サイズ・時間の見積りは停留所数に支配されるが、**この作業環境にはGTFSが無く実測
できなかった**。Macで以下を実行すると判断材料が出る(読み取り専用・出力変更なし):

```
python3 gap_map/estimate_stop_level.py
```

出力: 地区ごとの徒歩圏内停留所数(のりば統合後)/追加ファイル数/
現行地区JSONサイズからの外挿による総量見積り/生成時間の概算。

### 着工の判断基準(推奨)

| 指標 | 進めてよい目安 | 超えたら |
|---|---|---|
| 追加データ総量(見積り) | ≤ 150MB | 案B(主要2〜3停)に縮小 |
| 生成時間(Mac) | ≤ 2時間 | 同上 |
| 検算 | 「代表点の最寄り停」を選んだ結果が現行の地区JSONと一致すること | 原因究明まで着工しない |

GitHub Pagesの制限(サイト1GB・1ファイル100MB)には収まる見込みだが、
**gitの履歴は再生成のたびに肥大する**。着工時は「停留所データは再生成で全洗い替えに
なる」前提でコミット粒度を決めること(必要なら Git LFS も検討)。

## 6. 実装した軽量版 F10-L(2026-08-21。フル版は保留のまま)

### 6.0 きっかけ(2026-08-21 開発者要望)

> やっぱり、最寄りのバス停は目的地に合わせて、現在位置情報から
> 最寄りのバス停を検出できるようにできませんか?

§2 の案A(停留所単位の事前計算)は実測見積り296〜423MBで着工基準(150MB)を
超えたため保留中(handover §2)。しかし要望の中身=「**目的地に合わせた**最寄りの
バス停を**現在位置から**検出する」は、**すでに配っているデータ(`board_options`)だけで
実現できる**ことが分かったため、フル版を待たずに軽量版として実装した。

### 6.1 考え方

- 各便は `board_options`(=その同じバスが通る、家の徒歩圏の停+**その停での発車時刻**+
  徒歩分。近い順・最大6件)を持っている。これは「この行き先へ行くバスが実際に停まる
  バス停」の一覧そのもの
- したがって候補を **表示中の行き先の便から作れば、それが「目的地に合わせた最寄りの
  候補」**になる。どれを選んでも必ずその行き先に行ける(=一般の最寄りバス停検索と違い、
  「近いが目的地へ行かない停」を出さない)
- 距離は `stops_index.json`(停名→座標)と GPS の測位から直線距離で出す。
  **並べ替えと距離表示だけで、経路の計算はブラウザでしない**(設計原則3.3の範囲内)
- 選ばれた停への付け替えも、`board_options` に入っている**実測の発車時刻への差し替え**で、
  新しい計算ではない(しっかりモードの既存の絞り込みとまったく同じやり方)

### 6.2 実装(データ再生成なし・webapp のみ)

| 画面 | 追加したもの |
|---|---|
| かんたん・画面3 | **のりかたカードの上**に「いまいる場所から いちばん近いバス停」欄。📍で測位 → 最寄り停・距離・この日の本数・「◯◯へ行くバスが とまるバス停の中から えらびました」を表示。「「◯◯」から のる」で時刻表をその停のものに切り替え、「おすすめの「△△」に もどす」で復帰 |
| しっかり | 既存の「のるバス停で絞り込み」に📍ボタン。押すと候補を**近い順に並べ替え**、各チップに距離、先頭に「いちばん近い」。帰りの「おりるバス停」も同じ(見出しに「(いまいる場所から近い順)」と基準を明記) |

- 画面1の📍で測ったばかりの位置(10分以内)があれば、画面3では**押さずに**最寄りが出る。
  QR・リンクで画面3に直接来た人のために、画面3にも📍を置いた
- **自動では切り替えない**(GPSの誤差への保険。地区候補と同じ流儀)
- 位置情報が使えない端末・拒否された場合は欄ごと出さない/正直に伝えて従来動作に戻る
- GPSで停を選んだときは、①の「あるいて約◯分」(=地区代表点からの目安)を出さず、
  実測の「いまの場所から およそ◯m」だけを出す(基準の違う数字を並べない)。音声も同じ

### 6.3 途中で見つかった既存の不具合(あわせて修正)

`board_options` は停留所ID単位で作られるため、**同じ名前で のりばが複数ある場所**
(山形駅前など)では、1本の便が同じ名前の停を2回通ることがある
(行き47,532便中3便、帰り69,100便中286便)。しっかりモードの絞り込みは
最初に見つかった要素を採っていたため、たとえば d19→f27 で「山形駅前」を選ぶと
**11:53発(=同じバスが先に通るのりば)**が表示されていた(正しくは12:30発でも同じ便に乗れる)。

修正の規則(かんたん・しっかり共通):

- 乗車側は「その名前で乗れる**最後の発車**」=待ち時間が最短
- 降車側は「その名前で降りられる**最初の到着**」=いちばん早く家に着く
- どちらも同じ便なので、反対側の時刻は変わらない

### 6.4 この軽量版の限界(フル版=案Aが要る部分)

1. 候補は「**その行き先へ行く、時刻表に載っている便が通る停**」に限られる。
   家のすぐ前にバス停があっても、その停を通るバスがこの行き先へ行かない
   (=工場が採用しなかった)なら候補に出ない
2. かんたんモードの行きは `kantan_board` を通る便に絞られているため、
   「別の停は通るがおすすめ停は通らない便」は候補にも出ない(=停ごとの完全な時刻表ではない)
3. 距離は直線距離。川・線路・坂は考慮しない(README 既知の限界1と同じ)

1・2を完全に解くには停留所単位の事前計算(案A)が必要で、判断基準は §3 のまま。
**フル版が入ったときは、この軽量版のUIをそのまま使い、候補の作り方だけ差し替えればよい**
(候補=`{停名, 本数, 徒歩分}` の一覧 → 距離で並べ替え、という形は変わらない)。

### 6.6 気づいてもらえなかった問題への手当て(2026-08-22)

公開後、開発者から「『今いる場所から探す』しか出なくて、しかも地区のままですよ」との報告。
機能自体は動いていたが、**利用者が画面1で止まっていて画面3の欄に到達していなかった**。
原因は3つあり、すべて手当てした。

| 原因 | 手当て |
|---|---|
| 画面1の📍が「いまいる場所から さがす」としか書いておらず、バス停を探すボタンだと誤解する | 文言を「📍 いまいる場所から **地区を**さがす」に。候補の下に「このあと 行き先をえらぶと、いまいる場所から いちばん近いバス停を お知らせします」を追加 |
| 画面3の欄を のりかたカードの**下**に置いていたため、スマホ(390×844)では画面外だった | 欄を**カードの上**に移動。行数を抑えた作り(測位前=ボタン1つ+説明1行、測位後=2〜3行)にして、カードを画面外へ押し出さない。実測でy=176px・高さ230pxに収まることを確認 |
| 測位前は ボタンだけで、何ができる欄か分からなかった | ボタンの下に「◯◯へ行くバスが とまるバス停の中から さがします」を明記。さらに**すでに位置情報を許可している端末では、押さなくても自動で最寄りを出す**(Permissions API で `granted` のときだけ。未許可の端末に勝手に確認を出さない。API非対応の端末はボタンのまま=従来動作) |

あわせて、**古い index.html がキャッシュされていても機能が消えない**ように、欄の要素が
無ければJSが作ってのりかたカードの前に差し込む形にした(配信・ブラウザのキャッシュは
index.html と app.js で更新のタイミングがずれることがあるため)。
また、行けない行き先で早く return する経路で乗車停の選択が残る状態漏れも直した。

### 6.7 「家の最寄り停が、そもそも時刻表に無い」問題(2026-08-22に判明)

開発者から「いま山形県立中央病院にいるのだけど、最寄りのバス停として出てこない」
「自分の家の最寄りのバス停が山形県立中央病院という場合もあるじゃない」との指摘。
調べたところ、**F10-Lの実装の問題ではなく、家側の事前計算の根本にある制約**だった。

#### 何が起きているか

- 家側(行き)の乗り場候補は「**地区の代表点(=人口最大メッシュの中心)から徒歩800m
  (config.MAX_WALK_TO_STOP_M)以内**」の停に限られる(build_origins / district_near)
- 楯山地区(d17)の代表点から「県立中央病院」バス停までは **1,274m**。よって
  この停は d17 の時刻表に1便も載らない。**全41地区どこの時刻表にも載っていない**
  (実測: 0件)
- 一方 `webapp/data/karte.json` はメッシュ単位で計算しているため、病院周辺の
  住民メッシュの `nearest_stop_name` は正しく「県立中央病院(徒歩4分)」になっている。
  カルテと時刻表で答えが食い違う

#### 実測(この環境で webapp/data から測定・GTFS不要)

| 指標 | 値 |
|---|---|
| 徒歩圏にバス停がある住民メッシュ | 616 |
| ① 自分の最寄り停が、自分の地区の時刻表の乗り場候補に入っている | **206(33.4%)** |
| ② 入っていないが、他の地区の時刻表には入っている | 51(8.3%) |
| ③ **どの地区の時刻表にも入っていない** | **359(58.3%)** |
| stops_index の停(390)のうち、行きの乗り場として一度も出てこない停 | 118(30%) |
| 楯山地区(d17)のメッシュ20個のうち、代表点から800m超 | **15個(75%)**・平均1,154m・最大1,767m |

つまり**「表示される乗り場が自分の最寄りではない」ほうが多数派(3人に2人)**。
サブ地区分割(対策2)の基準が `FAR_DIST_M=2000m`(=代表点から2km超に300人以上かつ20%)
なので、楯山地区のように「1km前後に散らばる」地区は分割対象にならず、この問題が残る。

#### いま入れた手当て(アプリ側だけ・再生成なし)

嘘をつかないようにした。索引の全停(約390)から**ほんとうの最寄り停**を出し、それが
この時刻表の候補より100m以上近ければ、言い方を変えて正直に伝える:

> この時刻表で のれるバス停のうち、いちばん近いのは「漆山住宅入口」約1.7km
> いまいる場所の すぐ近くには「県立中央病院」(約100m)が ありますが、
> そのバス停から のる時刻表は まだ ありません。下の電話番号で ごそうだんください

しっかりモードにも同じ注記を出す。**問題は解決していない**が、利用者が
「壊れている」と受け取るのを防ぎ、電話相談に誘導できる。

#### 本当に直す道(いずれもMacでの再生成が必要)

代表点を増やす(=家側の出発点を細かくする)以外に手はない。必要な代表点の数と
データ量の見込み(現状 54単位・50MB、1単位平均954KBからの外挿):

| 徒歩圏の基準 | 住民メッシュの何%を圏内に | 必要な単位数 | 見込み総量 |
|---|---|---|---|
| 800m | 100% | 217 | 約202MB |
| 800m | 90% | 178 | 約166MB |
| 800m | 80% | 144 | 約134MB |
| 1,000m | 90% | 158 | 約147MB |
| 1,200m | 90% | 109 | 約102MB |
| **1,500m** | **90%** | **89** | **約83MB** |
| 1,500m | 80% | 74 | 約69MB |

- 案A: `make_subdistricts.py` の `FAR_DIST_M` を 2,000m → 1,200〜1,500m に下げ、
  分割基準(FAR_POP_MIN=300人・FAR_RATIO_MIN=20%)も見直して**サブ地区を増やす**。
  既存の仕組みのパラメータ変更だけで済み、UI・URL・QRは不変。上表の 83〜102MB が目安。
  **2026-08-22: コードを書き換えずに試せるようにした**(既定値のままなら従来と完全に同じ結果):

  ```
  # 採点表を見るだけ(何も書き換えない)。基準を変えて何地区が対象になるか試せる
  python3 gap_map/make_subdistricts.py --far-dist 1200 --far-pop 150 --far-ratio 0.10 --max-k 6
  # 納得したら分割を実行
  python3 gap_map/make_subdistricts.py --apply --far-dist 1200 --far-pop 150 --far-ratio 0.10 --max-k 6
  ```

  `--max-k` を3より大きくできるよう、kの昇格(従来は2→3の1段)を「基準を超える

  山形の確定値のままであること・基準を緩めると対象が増えること・冪等性)。
